# harness/ — Simple War agent harness

Client-agnostic tooling for agent work on this repo: telemetry, cheap tools, delegation, benchmarking, reflection.
Design and the reasons behind it: [DESIGN.md](DESIGN.md). Work items: `bd list -l harness`.

## Run
| Shell | Command |
|---|---|
| Git Bash / WSL | `harness/bin/hx <verb>` |
| PowerShell | `harness\bin\hx.ps1 <verb>` |
| cmd | `harness\bin\hx.cmd <verb>` |

The first run creates `harness/.venv` via uv. Every verb takes `--json` (machine-readable) and `-v` (show passing checks too). Exit code is 1 if any check FAILs.

## Verbs
| Verb | Does |
|---|---|
| `status` | Branch, dirty files, last commit, Godot version, autoloads, main-scene sanity, ready/in-progress tasks. `--no-tasks` skips bd. |
| `doctor` | Toolchain (git, uv, bd, rtk, Godot), checks `harness/data/` is git-ignored, scans committable files for API keys. |
| `report` | Spend (API-price estimate), tokens, cache hit, cost per closed task, friction, agent-vs-waiting time, and tables by day, model, task, tool and command. `--since 7d\|24h\|all\|YYYY-MM-DD` (default 7d). `--html` writes `data/reports/report.html`; `--open` also opens it. |
| `bench` | Benchmark ladder (DESIGN.md §8). `bench list`; `bench run --target bonsai [--level L1,L2] [--task 'L1-*-s'] [--context 0,8k,32k] [--repeat N]`; `bench report [--by target,level,size]`. Targets live in `config/bench_targets.toml`. |
| `providers` | The provider roster from `config/providers.toml`: readiness, monthly budget (default $0 with hard stop), free-tier limits, whether the free tier trains on your data. `--checklist` prints setup steps for providers that aren't ready. |
| `secrets` | `secrets set NAME` stores an API key in Windows Credential Manager (hidden prompt; `--file` stores it in `~/.hx/secrets.env`; `--stdin` reads it from a pipe). `secrets list` shows where each key comes from, never the value. `secrets delete NAME`. Lookup order: environment variable, then keyring, then file. |
| `gateway` | Local LiteLLM gateway on `127.0.0.1:4000/v1`.<br>• `start` / `stop` / `status` (usage per provider today, the month's spend, refusals, and whether calls are currently allowed).<br>• `config` regenerates `data/gateway/litellm.yaml` from `config/providers.toml`.<br>• `discover <provider> [--free]` lists a provider's models so you can fill in its `models` entries.<br>Clients authenticate with the `HX_GATEWAY_KEY` stored in the keystore. Models are served as `<provider>/<alias>`, e.g. `bonsai/nothink`. Over-budget or over-quota calls get a 429 with the reason. |
| `bonsai` | Local Bonsai llama-server.<br>• `start [--ctx N]`, `stop`, `status` (VRAM). Flags come from `[provider.bonsai.server]` in `providers.toml`; `--agent` is refused.<br>• `probe [--sizes 200k,…] [--apply]` loads each size, fills about 90% of it, and picks the largest context that keeps at least 95% of peak generation speed. Results go to `data/bonsai/probe-*.json`. |
| `delegate` | Hand a task to the cheapest model `config/routing.toml` trusts with it (DESIGN.md §7).<br>• `delegate --level L1 --class csv_to_json [--size s\|m\|l] [--input FILE] "task"` (or the prompt on stdin).<br>• Lookup order: the exact route; then the same class at a larger size; then any model that is `auto` on every route of the level. The size is guessed from the prompt length when omitted.<br>• Candidates are tried in order. A down local model is started when about 11 GB of VRAM is free; gateway 429s and errors fall through to the next candidate.<br>• Output: the model's text goes to stdout and a status line to stderr. Exit 2 = **escalate** (no trusted model; do it yourself). A `review` route prints `REVIEW IT`.<br>• `--model nous/qwen4-max` pins one routed model (its best usable entry on the level, else any route; exit 2 if none).<br>• `--agent` runs headless OpenCode on the first routed model it can drive (`opencode.json`: Bonsai, Qwen4 Max); it edits the working tree.<br>• Each call is logged without its text to `data/raw/delegate/`. |
| `mcp` | Stdio MCP server exposing the `delegate` tool. Registered for Claude Code in the repo's `.mcp.json`. |
| `worker` | Background job queue (SQLite `data/worker/queue.sqlite`) and Bonsai lifecycle.<br>• `enqueue <kind> [--payload JSON] [--hook]`, `tick [--force]`, `start`, `stop`, `status`, `run [--once]`.<br>• Jobs: `ingest`; `session_end` runs ingest and then the follow-ups (`tag_session`, `mine`, `reflect`).<br>• `tick` queues the same follow-ups on a clock, at most every 6 h, for sessions that never end: `mine`, `reflect`, and tagging for up to 5 untagged sessions with no call for 12 h. It starts the worker if it queued anything. A tag job for a session that wrote no transcript is skipped.<br>• Local jobs start Bonsai only when about 11 GB of VRAM is free. Bonsai is stopped after 10 idle minutes, but only if the worker started it.<br>• The worker exits after 15 minutes with an empty queue, stopping the Bonsai server and the gateway if it started them; `tick` and the SessionEnd hook start it again. Background processes are spawned with a hidden console (`CREATE_NO_WINDOW`), so nothing they start opens a terminal window.<br>• `hx delegate` holds a lock that pauses local jobs.<br>• Fed by the Claude Code SessionEnd hook and the OpenCode plugin `.opencode/plugins/hx.js`. |
| `tag` | Session tags (DESIGN.md §3; taxonomy in `config/taxonomy.toml`).<br>• `tag <session_id> [--force]`, `tag --untagged [--limit N]`, `tag --report` (counts, friction by kind, tagger-vs-audit agreement).<br>• The tagger is routed through `hx delegate` (L3/session_kind, so Bonsai). It reads the human prompts, the final reply and ledger stats.<br>• Friction is computed from tool errors, denials, interrupts and compactions.<br>• A deterministic 10% of sessions is re-tagged by Sonnet as an audit.<br>• Rows go to `data/raw/tags/`. The worker tags each finished Claude Code session. |
| `mine` | Repetitive-task mining (DESIGN.md §5).<br>• `mine` lists repeated command shapes (e.g. `git add && git commit && git push`; `cd`, pipes and single read commands are dropped) seen in at least 3 sessions and 5 uses.<br>• `mine --file` files new shapes as bd tasks labelled `mined`, at most 3 per run, with a verb name proposed by the local model.<br>• `mine --report` shows uses and tokens per hx verb, plus each mined shape's baseline cost.<br>• The worker runs it after sessions, at most every 6 h. State is in `data/mining/state.json`. |
| `reflect` | Weekly reflection, proposals only (DESIGN.md §9).<br>• `reflect --evidence` prints the week's evidence pack.<br>• `reflect [--dry-run]` has Sonnet propose at most 5 changes citing that evidence. They are filtered (evidence, area, duplicates, money) and filed as bd tasks labelled `reflection`.<br>• The worker runs it at most every 7 days. Runs are kept in `data/raw/reflection/`. |
| `task` | The tracker interface (DESIGN.md §10), an adapter over bd today.<br>• `ready` (epics hidden), `show <id>`, `claim <id>`, `close <id> [--reason]`, `new "title" [-d] [-p] [-t] [-l] [--parent]`, `note <id> "text"`. |
| `godot` | `check [--no-import] [FILE...]`: headless import plus a GDScript parse of every script under `src/`, or only the FILEs (no import). Prints errors only, with locations, deduplicated.<br>**Native-method lint:** the engine's parse is not type-aware, so `c.to_global()` on a `Control` passed and failed at runtime. check also runs `harness/godot/native_method_lint.gd`, which finds variables declared with a native class (params, `var x: T`, `var x := T.new()`) and asks ClassDB whether `T` has each method called on them (per function, heuristic; script-class types are skipped). Untyped receivers are not covered: rely on `hx godot test` and typed variables.<br>`test [--dir D] [--file F] [--select S] [--test T]`: GUT headless, all or a subset; prints the summary and failures, and warns when nothing matched.<br>`run <scene\|script> [--quit-after N] [--tail N] [-- args]`: one scene or SceneTree script headless; errors plus the last lines of output, and on timeout what it printed so far. `run --editor` starts the editor headless so plugin errors show. `run --windowed` (sw-tho3.14) keeps a real renderer for the capture runner (`src/presentation/capture/capture_runner.gd` draws PNGs; `--headless` draws nothing).<br>`mock <res://…_mock.gd>`: UI mock to PNG. Paths are `res://…` or repo-relative. Always also writes `<name>_greyscale.png`, `<name>_protan.png`, `<name>_deutan.png` beside the normal PNG (WCAG luminance; Machado 2009 severity-1.0 matrices in linear RGB, `src/presentation/mocks/cvd_sim.gd`) to catch colour-alone failures; the normal PNG is unchanged. A battle mock (one with a ContextView) also writes `<name>_layout.json`, the rectangles it drew, for `hx visual lint`. |
| `ab` | `ab rtk`: the rtk A/B experiment. Per arm: sessions, Bash calls, output tokens per call, error rate. Verdict `collecting` until 10 sessions per arm, then `keep` (≥ 20% saved, no more errors) or `drop`. Arms come from `bin/rtk-hook`; force one with `HX_RTK=on\|off`. |
| `otel` | OTLP receiver for Claude Code telemetry, http/json on `127.0.0.1:4318` (DESIGN.md §2).<br>• `start` (also run by the SessionStart hook), `stop`, `status`, `serve`.<br>• Raw payloads go to `data/raw/otel/`, with account identity removed.<br>• Ingest adds only API latency, tool run time and success, permission decisions, active time and lines changed, as events. |
| `sim` | Game harness runs (GDD 05 §5.1-5.2), results in DuckDB `data/sim.duckdb` (separate from the ledger).<br>• `sim run <scenario>... [--variant NAME]... [--seeds 4\|3-6\|1,5] [--jobs 4]` plays scenario × variant × seed headless, one Godot process per run (`res://src/api/sim_runner.gd`), then prints the batch summary. Scenarios are battle scenario or overworld map IDs.<br>• Variants live in `data/sim/variants/<name>.json` (content patches and controller profiles); `baseline` is the content as shipped.<br>• `sim report [--batch ID] [--metric 'band.morale.%']`, `sim list`, `sim variants` (and labs).<br>• `sim lab <lab> [--seeds] [--jobs]`: the Pressure Lab (GDD 05 §5.3). It sweeps a lab's parameter axes (`data/sim/labs/*.json`) as generated variants, then shows per setting which tropes (`data/sim/tropes.json`) emerge. `sim tropes [--batch]` re-evaluates them.<br>• `sim fitness [--batch] [--spec default] [--generation G] [--hof-rate R]`: AI factory fitness (GDD 05 §5.4). It scores a batch's runs from their metrics and per-turn series (`sim_series`) under a spec (`data/sim/fitness/<spec>.json`) and criteria library (`data/sim/criteria.json`), stores the parts in `sim_fitness`, and prints fitness, its parts and behaviour descriptors per scenario × variant × player. `sim run` and `sim lab` score their batch under the default spec as they finish.<br>• Each run's JSON report and replay save are kept in `data/sim/runs/<batch>/`. |
| `factory` | The AI factory's evolution loop (GDD 05 §5.4), results in the same DuckDB (`factory_*` tables).<br>• `factory run [--generations N] [--seed S] [--scenario MAP] [--pairings P] [--seeds K] [--population N] [--jobs J] [--set KEY=VALUE]` evolves controller-profile genomes by competitive co-evolution: age-weighted pairings on both sides, one harness batch per generation, fitness under the default spec, hall of fame, MAP-Elites archive, lineage (`harness/src/hx/factory.py`). A run is reproducible from its seed.<br>• `--intensity background|normal|max` sets the parallel Godot processes (1-2 at below-normal priority / half the cores / about 90%).<br>• `factory stop [--run ID]` (or Ctrl+C) lets running matches finish, saves them and exits; `factory resume [--run ID] [--generations N]` plays only what is missing and continues, with the same results as never stopping.<br>• `factory report [--run ID]`: per-generation stats, the archive, the hall of fame and the scoring-gain rate; works while a run plays. `factory list`: runs. |
| `autopilot` | Headless Claude Code on the `bd ready` backlog, one bead at a time, inside the Claude plan's limits (`src/hx/autopilot.py`, caps in `config/autopilot.toml`).<br>• `start` / `stop` (`--after-bead`: the running bead finishes, no other starts) / `status`; `run [--once] [--bead ID]` in the foreground; `probe` reads both plan windows now with one haiku call.<br>• Each bead: `bd update --claim`, a worktree `../simple-war-worktrees/ap-<bead>` on branch `autopilot/<bead>`, then one `claude -p` session (auto permission mode, Haiku at high effort; large or long-horizon beads, by `[claude.large]` label or description length, on Opus at medium effort, which plans and hands pieces to Haiku subagents; a turn and wall-clock cap). Claude commits on the branch and ends with `RESULT: done\|partial\|blocked`; Haiku may answer `RESULT: escalate` (or time out) to move the bead to Opus without using up an attempt.<br>• `done`: the swarm's merge gate (`swarm.merge_branch`: main merged in, `godot check`/`test` or pytest on the result, fast-forward, push) and `bd close`. `partial` or a failed merge: the bead is unclaimed and the branch kept for the next attempt; after `max_attempts` it is labelled `autopilot-failed`. `blocked`: labelled `autopilot-blocked`. Every outcome is appended to the bead's notes.<br>• Limits: readings come from the status line and from every headless turn's rate-limit events (`data/raw/quota/claude-pro.jsonl`). A bead starts only while the 5-hour window is under `five_hour_start_pct` and the weekly window under a pace line (`weekly_max_pct` spread over the week plus `weekly_slack_pct`); a running session is ended, its work kept as a `WIP(<bead>)` commit, when the 5-hour window passes `five_hour_stop_pct`. A cut for limits or a stop does not use up an attempt.<br>• Picks like the swarm's auto-refill (priority, bugs first; no epics, parents, design interviews or excluded labels) and skips beads whose named paths overlap a swarm worker's. State and logs: `data/autopilot/` (`events.jsonl`, `jobs/`, `logs/<bead>/*.jsonl` stream-json transcripts). |
| `workshop` | Behaviour workshop (`data/sim/workshop/`, format in its README; `src/api/workshop/`).<br>• `list`: one row per scenario file (status, component, variant and check counts).<br>• `run <id> \| --all [--variant V] [--trace] [--json]`: runs `workshop_cli.gd` headless through `hx godot run`'s plumbing and prints one line per scenario, failures first; a failing probe or comparison is listed under its scenario. `--trace` also lists every passing, pending and report-only check.<br>• Exit 1 only when a gate check fails or a scenario cannot load or run; pending checks never do. Exit 2 is a usage error (unknown id, or an id with `--all`). |
| `visual` | Visual assessment of battles (draft 02 §5.6). `lint` and `diff` are built (sw-tho3.12, sw-tho3.13; `--metric ssim` sw-tho3.14).<br>• `diff <capture> --golden NAME [--accept]` (sw-tho3.13, `hx/golden.py`): exact per-pixel diff of a capture (a path, or a name under `data/visual/`) against the golden set `data/visual/golden/NAME/`. Tolerances in `config/visual.toml` `[golden]`: a pixel is changed above `max_channel_delta` (8), and a shot is over tolerance above `max_changed_share` (1% of pixels). Over-tolerance and size-mismatch shots exit 1; diff PNGs (changed pixels in magenta) go to `data/visual/diff/NAME/<capture>/`. `--accept` replaces the golden set with the capture. Golden sets are per machine and `data/visual/` is git-ignored. No new dependency: the stdlib PNG reader from `hx/visual.py`.<br>• `diff ... --metric ssim` (sw-tho3.14, perceptual): both captures are box-blurred (radius 1, absorbs anti-aliasing and dither), then SSIM over 16 px tiles per colour channel (the lowest kept). A tile is changed below `min_block_ssim` 0.9; a shot is over above `max_changed_share` 0.10% of tiles (`[golden.perceptual]`). Calibrated on real `attack_move_firing_position` stills (one machine; noise at most 0.04% of tiles, label moves, hidden labels, recolours and a different battle at least 0.29%). Stdlib only (`hx/golden.py`). Exact pixels stay the default: at 1% of pixels they cannot separate AA noise from a moved label, see sw-tho3.14 notes.<br>• `lint <layout.json \| capture-dir \| mock-dir> [--png IMAGE] [--strict]`: model-free layout checks on the rectangles the battle view drew (`layout/<shot>_<kind>.json` from `capture_runner.gd`, `<name>_layout.json` from a battle mock). Finds label against label overlap (over 10% of the smaller label), a label over another squad's footprint (over 10% of the label), footprints overlapping (over 25% of the smaller), and label text contrast below WCAG AA 4.5:1 over the ground under it (the ground is the most common colour in the label's rectangle; luminance weights as `cvd_sim.gd`). Findings are warnings: exit 0 unless `--strict`. Exit 2 when no layout is found.<br>• Pure stdlib (its own PNG reader), in `src/hx/visual.py`. Capture, ask and report (V8 to V10) are not built. |
| `ingest` | Copies new Claude Code transcripts and exports changed OpenCode sessions (session tables only) to `data/raw/`, then loads them into the DuckDB ledger (`data/ledger.duckdb`). Incremental. `--rebuild` re-reads all raw copies, e.g. after a schema change. |

## Live monitoring (wired in `.claude/settings.json`)
- **Status line:** `bin/statusline` runs `python -m hx.statusline`, about 210 ms. Example:
  `Opus 5.5 · 5h 42% ↺14:20 · 7d 18% ↺Thu · ctx 34% · sess $1.20 · today $8.45 · $1.12/task`.
  - Quota windows appear only on Pro, Max or Ultra plans, after the session's first response. `⚠ full ~HH:MM` means the current burn rate hits 100% before the window resets.
  - Each refresh appends a quota snapshot to `data/raw/quota/claude-pro.jsonl` (only when the value changed, or every 5 min). `today $` comes from `data/cache/summary.json` and gets a `?` when that cache is older than 6 h.
  - The status line never opens the ledger.
- **Stop hook:** runs `hx ingest` and then `hx worker tick` asynchronously after every turn, so the ledger and the summary cache stay current and the follow-up jobs run during long sessions.

## Benchmark suite (`bench/`)
- **Tasks:** `bench/tasks/<level>/*.json` hold suite v1, 20 tasks, generated by `hx.bench.fixtures` from a fixed seed and then frozen.
  - L1: CSV→JSON, JSON→Markdown table, rename/drop keys and filter/sort, each in sizes s, m and l.
  - L2: attack entries filled in to `bench/schemas/attack.schema.json`.
  - L3: Godot log triage, session-kind tagging, and classifying commands as read-only or mutating.
- **Checking:** purely mechanical (exact JSON, table rows, sets, label accuracy, schema plus fields). No LLM judge.
- **Context padding:** `--context` pads the prompt with a frozen GDD copy (`bench/filler/gdd.txt`) up to roughly N tokens.
- **Results:** appended to `data/raw/bench/<run_id>.jsonl`, including the full model output.
- **Report:** pass rate per group, with a routing verdict: `auto` at ≥ 90%, `review` at ≥ 70%, otherwise `no`.
- **Routing:** `hx bench route [--write]` builds `config/routing.toml` from all results for the current suite. Per (task class, size), it picks the cheapest tier whose pass rate is `auto` (local, then free api/client, then subscription); ties go to the higher pass rate, then the faster target. Only ctx-0 runs count toward the rate; context sweeps set `max_ctx_passed`. The file is generated: re-run the ladder and regenerate instead of editing it.
- **Changing the suite:** never edit task files. Bump `SUITE_VERSION` and run `hx bench build --force`; a test fails if the frozen files drift from the generator.
- **Haiku target:** uses the `claude` CLI on your subscription. It needs `claude auth login` once in a terminal.

## Ledger
`data/ledger.duckdb` is derived; the raw copies under `data/raw/<client>/` are the durable record.
Tables:
- `session`
- `call`: one row per model response, deduped by message id, with tokens and `est_usd`
- `tool_use` and `tool_result`
- `event`: prompt, interrupt, api_error, turn, compaction
- `session_task`: linked from `bd update <id> --claim` and `bd close <id>` commands
- `quota_snapshot`
- `import_state`

View: `session_summary`.

Prices live in `config/prices.toml`; every ingest re-prices all calls, so editing prices needs no rebuild. To query the ledger directly: `uv run --project harness python -c "import duckdb; print(duckdb.connect('harness/data/ledger.duckdb', read_only=True).sql('select * from session_summary'))"`.

## Layout
```
bin/            shims (bash, cmd, ps1)
src/hx/cli.py   verb dispatcher; add a verb = add hx/commands/<verb>.py + list it in VERBS
src/hx/output.py Result/Check contract: compact text by default, JSON with --json
tests/          pytest (run: uv run --project harness pytest)
data/           ledger + raw transcripts (git-ignored)
```

## Adding a verb
1. Create `src/hx/commands/<verb>.py` with `HELP`, optional `add_args(parser)`, and `run(args) -> Result`.
2. Add it to `VERBS` in `cli.py`.
3. Add a test in `tests/`.

Keep the default output short: agents pay for every line. Hide passing checks unless `-v` is given.

Mark a known-fake key in a fixture with `hx-allow-secret` on the same line, so the scan skips it.
